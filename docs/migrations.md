# Database migrations (Drizzle)

Source of truth for the schema is `apps/api/src/infrastructure/database/schema/*`.
Migrations live in `apps/api/drizzle/` (SQL files + `meta/_journal.json` + `meta/NNNN_snapshot.json`).
Pinned tooling: `drizzle-orm` 0.39.3, `drizzle-kit` 0.30.6 (see `pnpm-lock.yaml`).

## Scope of the metadata repair

> **This repair migrates no database and establishes no baseline.**
> It only makes the migration *metadata* in git consistent. No PostgreSQL,
> PGlite or other database was connected to, migrated, reset or deleted. How
> migrations get applied to a real database is a separate, later step.

## Historical inconsistencies that were found

1. **Wrong journal tag.** Journal entry idx 5 said `0005_fine_siren`, but the file on disk is `0005_cynical_shiva.sql`. Drizzle's migrator throws when it cannot read the SQL file for a journal entry.
2. **Missing journal entries.** `0006`–`0010` existed as SQL files but were never added to the journal, so Drizzle's migrator never discovered them (only `0000`–`0005`).
3. **Stale snapshot.** The latest snapshot was `0005`. `drizzle-kit generate` therefore diffed the current schema against an outdated state and would have produced a *duplicate* `0006_*.sql` re-adding changes that already exist in `0006`–`0010`.
4. **Hand-written migrations.** `0006`–`0009` were written by hand, so no snapshots exist for them.

## What the repair did

- `meta/_journal.json`: fixed the idx 5 tag to `0005_cynical_shiva`; added entries idx 6–10 in SQL-file order. Timestamps (`when`) of idx 0–5 were left untouched.
- New `when` values follow one policy: **`max(committer time of the commit that introduced the SQL file, previous when + 1 ms)`**, so values are unique and strictly increasing even when several files were added in one commit.

  | idx | tag | when |
  |---|---|---|
  | 6 | `0006_class_sessions_unique` | 1791099122000 |
  | 7 | `0007_teacher_attendance_unique` | 1791099122001 (tie-break +1 ms) |
  | 8 | `0008_payrolls_unique` | 1791099122002 (tie-break +2 ms) |
  | 9 | `0009_class_color` | 1791611461000 |
  | 10 | `0010_class_name` | 1791690111000 |

- `meta/0010_snapshot.json`: generated by the pinned drizzle-kit in an isolated scratch copy and copied byte-for-byte. Its `prevId` is the id of snapshot `0005`. Compared with `0005`, it adds exactly: `classes.name`, `classes.color`, the `payrolls` unique constraint and the `teacher_attendance_records` unique constraint — i.e. what `0006`–`0010` do.
- **No intermediate snapshots (0006–0009) were fabricated.** Drizzle only needs the *latest* snapshot to diff against, and `drizzle-kit check` validates the chain of snapshots that exist. The allow-list of known gaps lives in `scripts/db-check.ts` (`KNOWN_MISSING_SNAPSHOT_IDX`); any other missing snapshot fails the check.
- The 11 `.sql` files were not modified (their hashes are what a database that already applied them has recorded).

### Why the `when` values matter

The installed Drizzle PG migrator applies a migration only if `last_applied.created_at < migration.when`, comparing against the **most recent** row in `drizzle.__drizzle_migrations`. Timestamps therefore must be strictly increasing in journal order, otherwise a migration can be silently skipped.

## Rules for future migrations

1. **Never hand-edit** `_journal.json`, snapshots, or an already-committed `.sql` file. Edit the schema in `apps/api/src/infrastructure/database/schema/` and let drizzle-kit generate:
   ```
   cd apps/api && pnpm exec drizzle-kit generate --name <short_name>
   ```
2. **Review the generated SQL** before committing (it should contain only the intended change). Commit SQL + journal entry + new snapshot together.
3. Run `pnpm db:check` and `pnpm test` before opening a PR.
4. Hand-written SQL (data fixes, etc.) is allowed only via `drizzle-kit generate --custom`, which keeps journal and snapshot consistent.
5. Never reorder, rename or delete a migration that has been merged.

## `pnpm db:check`

Offline: it never connects to a database and never reads `DATABASE_URL`. Its results are reproducible when the repository state, installed dependencies and the relevant clock value are held constant. It is not clock-independent: the check that `when` timestamps are not in the future compares them with the current system time, so it can fail if the system clock is set earlier than a journal timestamp. It verifies:

- every journal tag maps to an existing SQL file, and every SQL file appears exactly once;
- `idx` values are contiguous, tags are `NNNN_name` with prefix == idx;
- `when` values are strictly increasing, positive, and not in the future;
- the installed Drizzle migrator (`readMigrationFiles`) discovers every migration, in order, with matching timestamps, and a pending-migration simulation (fresh DB, or any prefix already applied) never skips one;
- snapshots: version/dialect match, unique ids, first `prevId` is the zero UUID, each `prevId` equals the previous snapshot's id, latest snapshot idx equals the last journal idx, only documented gaps;
- in an **isolated scratch copy in the OS temp dir** (repo untouched), `drizzle-kit check` reports "Everything's fine" and `drizzle-kit generate` reports "No schema changes, nothing to migrate" without creating files.

The tests are in `tests/unit/migration-metadata.spec.ts` (real files plus negative fixtures in temp copies) and run with the normal `pnpm test`.

## Database drivers (explicit selection)

The driver is chosen from the environment alone (`apps/api/src/infrastructure/database/driver-selection.ts`); a failed connection never changes it.

| Configuration | Result |
|---|---|
| `DATABASE_DRIVER=postgres` + postgres(ql):// `DATABASE_URL` | PostgreSQL (preferred) |
| `DATABASE_DRIVER=pglite` (no `DATABASE_URL`, or `pglite`) | Embedded PGlite, non-production only |
| `DATABASE_DRIVER=pglite` + a postgres URL, `postgres` without a postgres URL, `postgres` + `USE_PGLITE=true` | **Startup error** (conflict) |
| `NODE_ENV=production` with PGlite or with no database configured | **Startup error** |
| Legacy: only a postgres `DATABASE_URL` | PostgreSQL, with a warning to set `DATABASE_DRIVER` |
| Legacy: `DATABASE_URL=pglite` or `USE_PGLITE=true` | PGlite, with a deprecation warning |
| Nothing configured, non-production | PGlite, with a warning (explicit, not failure-driven) |

**Behaviour change:** if PostgreSQL is selected and cannot be reached, the API now fails to start (error message with the password masked). It used to log a warning and silently open PGlite instead. The old default `DATABASE_URL` in the env schema was removed for the same reason.

### PGlite bootstrap (development only)

Defaults are inert: with no flags the app opens the PGlite directory, requires the `accounts` table to exist, and otherwise fails with a clear message. Nothing is applied, seeded or deleted.

| Variable | Default | Effect |
|---|---|---|
| `PGLITE_DATA_DIR` | `./.pglite-storage` | Directory, or `memory` for an in-memory database |
| `PGLITE_AUTO_MIGRATE` | `false` | `true` replays every SQL file at startup. This is the old, untracked behaviour (errors containing "already exists" are ignored); use it for a fresh/throwaway dev database only |
| `PGLITE_SEED_DEMO` | `false` | `true` inserts demo accounts/data when `accounts` is empty (known demo passwords) |

The storage directory is **never** removed or reset automatically. Previously, any failure of the `accounts` query deleted `.pglite-storage` and rebuilt it.

For a first local run with PGlite: `DATABASE_DRIVER=pglite PGLITE_AUTO_MIGRATE=true PGLITE_SEED_DEMO=true`. An existing storage directory created before this change keeps working without the flags as long as it has the schema; it will not receive newer migrations automatically.

## `pnpm db:status` (read-only)

Reports which repository migrations are applied/pending in a database. It never applies, baselines, creates the history table or deletes anything.

```
pnpm db:status                       # PostgreSQL, from DATABASE_DRIVER/DATABASE_URL in the environment
pnpm db:status --pglite-dir <dir>    # an existing PGlite directory that you name explicitly
pnpm db:status --json
```

- All queries are fixed `SELECT`s, checked by `assertReadOnlySql`, inside a `READ ONLY` transaction that is rolled back.
- The environment is read as-is (no `.env` loading) and there is no fallback driver. Exit codes: `0` ok, `1` problems found, `2` configuration/connection error.
- Opening a PGlite directory may touch its files (PGlite recovery); inspect a copy if the data matters. A PGlite directory is never opened unless you pass `--pglite-dir`, and it is never created.
- It reports `state`: `empty`, `tracked` (Drizzle history present) or `untracked-existing-schema` (tables exist but no history, e.g. a database built by the old SQL replay). The last one is flagged as **not safe to migrate**: running the Drizzle migrator there would try to re-create existing tables.
- It also mirrors the installed migrator's skip rule (`last created_at < when`) and flags migrations that are pending but would be skipped, or applied but would re-run, plus applied hashes unknown to the repository.

`db:status` is the dry-run for migrations: there is no command in the repository that applies migrations to PostgreSQL yet. Use `db:baseline` (below) to record history for an existing untracked database.

## `pnpm db:baseline` (dry run by default)

For a database that has the application tables but **no Drizzle history** (for example one built by the old SQL replay). A baseline is a *claim* about existing state, so it is only recorded when that claim can be proven.

```
pnpm db:baseline --pglite-dir <dir>                         # dry run, read-only
DATABASE_DRIVER=postgres DATABASE_URL=... pnpm db:baseline  # dry run, read-only
pnpm db:baseline <target> --confirm-baseline [--target <tag>]   # the ONLY writing mode
```

- **Explicit target only.** PostgreSQL needs `DATABASE_DRIVER=postgres` itself (legacy inference from `DATABASE_URL` is rejected); PGlite needs `--pglite-dir` pointing at an existing directory (never created). There is no fallback driver, and it never runs at application startup.
- **Exit codes:** `0` allowed/recorded, `1` refused, `2` usage or connection error.

### How equivalence is proven
1. `validateMetadata` (the `db:check` rules) must pass for the repository; metadata is never repaired here.
2. The repository SQL is replayed one migration at a time in a fresh **in-memory** PGlite. After each migration the `public` schema catalog is fingerprinted: relations, columns (type, nullability, default, identity/generated), constraints (`pg_get_constraintdef`), indexes (`pg_indexes`), enum labels in order, triggers and function signatures.
3. The target database is fingerprinted the same way. It must be **identical** to exactly one of those 11 states. The baseline then records that many migrations and leaves the rest pending, so a database that is only at 0005 is baselined at 0005, not at 0010.
4. If the schema equals the state after several migrations (a schema-neutral migration), it is refused as ambiguous unless you pass `--target <tag>` naming one of the matching migrations.

### Refusal conditions (nothing is written)
Repository metadata invalid · database empty · any Drizzle migration history already present (no "merge" path) · unknown applied hashes · schema matches no migration state (the report lists the differences against the closest state) · ambiguous match without a valid `--target` · `--target` that contradicts the schema · an existing `drizzle.__drizzle_migrations` with unexpected columns · post-write verification not exactly as planned.

### What `--confirm-baseline` writes
Only the migration history, in a **single transaction**:
1. takes `pg_advisory_xact_lock` (serialises baseline attempts), then **repeats every check inside the transaction**;
2. `CREATE SCHEMA IF NOT EXISTS drizzle` and `CREATE TABLE drizzle.__drizzle_migrations (id SERIAL PRIMARY KEY, hash text NOT NULL, created_at bigint)`, the installed migrator's DDL without `IF NOT EXISTS`, so a concurrent creator makes it fail instead of being merged (an existing *empty* table with the right columns is reused);
3. one row per recorded migration: `hash` = sha256 of the SQL file and `created_at` = the journal `when`, exactly what the installed Drizzle migrator stores;
4. re-reads the status inside the transaction and rolls back unless exactly the planned migrations are applied, the rest are pending, and the migrator would run exactly those.

Application tables and data are never modified. A crash or error rolls the whole transaction back, so there is never partial history.

### Limits and recovery
- **Schema equality is not data equality.** Data-only migrations cannot be verified; the tool proves structure only.
- Catalog text (`pg_get_constraintdef`, `pg_get_indexdef`) can differ between PostgreSQL major versions; a false mismatch fails closed (refusal), never a false match.
- Only the `public` schema and migrations table are examined; objects elsewhere are not compared.
- The advisory lock stops two baseline runs, but does not block other sessions running DDL concurrently; run it in a quiet window.
- **Back up first.** To undo a baseline: `DROP TABLE drizzle.__drizzle_migrations` (and the `drizzle` schema if empty); nothing else was touched.
- Real PostgreSQL has not been exercised by the automated tests (only PGlite); try the dry run on a restored copy first.
